# Authenticated attachment API

The same bearer key protects ingestion and job status. Set a strong `API_KEY`
before starting the gateway. Do not put it in query strings or filenames. Use
HTTPS outside local development. A shared API key is a service credential, not
per-user authorization or tenant isolation; rotate it and restrict callers.
No wildcard CORS policy is configured. Browser access requires a reviewed,
explicit origin allowlist; do not embed the service API key in a public frontend.

## Submit

```sh
curl --fail-with-body \
  --oauth2-bearer "$API_KEY" \
  -F 'file=@./sample.pdf' \
  http://localhost:3000/attachments
```

Send exactly one multipart file. Do not set the multipart Content-Type manually:
`curl` must generate its boundary. The gateway bounds streamed input at 20 MiB
and checks at most 512 signature bytes. The client's filename, MIME type and
extension are untrusted hints, not parser selection authority. Storage names
must be generated by the service, not constructed from client path components.

An acknowledged accepted upload returns HTTP `202` with `fileId`, `status: QUEUED`,
`statusUrl: /attachments/{fileId}` and `pollAfterSeconds: 2`. Authentication,
multipart, size or signature validation errors must not enqueue a valid job.
This is not synchronous malware scanning: a `202` response does not permit
serving the original file.

### Ambiguous acceptance and retries

Queue publication and the HTTP response are not one atomic transaction. Redis
can commit a job and lose the acknowledgement; a `503` or lost response therefore
does **not** prove that no job was accepted. Once publication is attempted, an
error retains the quarantine input so a possibly committed job does not lose its
active input. Validation/storage failures before publication still attempt
cleanup. Unreferenced retained input expires under the quarantine lifecycle.

Delivery/processing must be treated as at-least-once, not exactly-once. Client
idempotency keys and an upload deduplication contract are **not implemented**.
Blindly retrying an ambiguous submission can create another job/file identifier.
Callers must apply their own retry/reconciliation policy; do not assume a supplied
filename, content hash or HTTP error creates server-side idempotency.

## Poll

```sh
curl --fail-with-body \
  --oauth2-bearer "$API_KEY" \
  http://localhost:3000/attachments/FILE_ID
```

Use the identifier from the submission response, and back off between polls.
Status endpoints never bypass authentication. Treat all nonterminal states as
pending, and only `CLEAN` as authorization to consume the rebuilt output.
`QUARANTINE_REJECTED` is terminal and must not be retried as an original-file
copy. Storage itself remains private; this API is not a public Blob proxy.

| State | Meaning |
| --- | --- |
| Pending / active | Stored or processing; not safe to distribute |
| `CLEAN` | Validated rebuilt output has been written |
| `QUARANTINE_REJECTED` | Validation, parser, sandbox or processing failure |

The exact terminal success discriminator is `CLEAN`. A clean result
also includes `outputMime`, `sha256`, `sizeBytes` and `cleanKey`; the latter is a
private object identifier, not a public download URL. Rejection includes a
`reason`. Pending responses use `QUEUED` or `PROCESSING`.

| HTTP response | Boundary meaning |
| --- | --- |
| `400` | Invalid multipart/request parameters |
| `401` | Missing or incorrect bearer credential |
| `404` | Unknown job identifier |
| `408` | Upload deadline exceeded |
| `413` | Input exceeds 20 MiB |
| `415` | Unsupported binary signature |
| `429` | Rate or concurrent-upload capacity exceeded |
| `503` | Infrastructure/queue operation failed; acceptance may be ambiguous |

Unknown jobs, queue failures and validation failures return boundary-mapped
errors; callers must not infer success from a missing response. A sandbox timeout,
process kill, malformed sandbox response or output-limit violation is rejection.
No caller should be able to learn another tenant's jobs from predictable IDs;
multi-tenant authorization would require a separate identity/ownership layer.

## Accepted transformations and limits

Supported types and exact output representations are determined by the parser
implementation. Signature acceptance is not permission to run a host parser:
all parsing and rebuilding happens in the isolated sandbox. Archives are not
general-purpose extraction services.

The fixed envelope is 20 MiB input, 32 MiB expanded data, 32 MiB output, 100:1
expansion, 128 archive entries, 20 PDF pages, 16 million image pixels, and a
15-second execution deadline. Traversal, absolute paths, symlinks and nested
archives are rejected. Never increase limits to make a rejected file pass without
reviewing resource and amplification risks.

Webhook fields or event concepts are reserved for future integrations. There is
**no implemented webhook dispatcher, delivery signature, retry contract or
callback allowlist**. Do not configure a callback and assume it will fire.
